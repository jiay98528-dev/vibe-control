# vibe-control 0.3.7 Windows 执行、证据闭包与 Dashboard 修复需求

## 目标

- 在不改写锁定逻辑命令的前提下，让 Windows 候选执行可靠解析 `pnpm/npm/npx/yarn` 等命令包装器，并保留参数边界。
- 让受管 execution evidence 的工作副本、Git blob 与 fresh checkout 使用同一字节身份，避免换行或 filter 转换制造伪漂移。
- 分离接入诊断 case 与候选执行 case，禁止控制面 bootstrap/DRAFT 自检进入产品候选的 required cases。
- 让 Dashboard 与 `validate` 消费同一份只读派生事实，不能用陈旧 declared state 或局部 evidence 显示假绿。
- 为 Schema 3.2 项目提供内容绑定、可回滚且不继承旧 PASS 的同 Schema runtime 升级路径。

## 固定边界

- 版本为 `0.3.7`，核心 Schema 保持 `3.2`；本次是运行时与兼容层修复，不是 Schema 3.1→3.2 migration。
- 包姿态保持 `DEVELOPMENT_DIAGNOSTIC`、`formalClaimsAllowed=false`，最高声明为 `DEVELOPMENT_CHECKED`。
- 不创建 release/audit tag，不把安装、升级、Dashboard 或控制项自测外推为 `FORMAL_GATE_READY`。
- 不修改 Pulse、VibeCodingGovernance 或 MarkLuck 产品代码；MarkLuck 只升级项目控制面、建立新任务和重跑已锁定的本地 case。
- 不重写 MarkLuck 既有提交，不 push、accept、tag、签名或 release；外部发行、真机和签名 case 保持待证。

## 机器契约

1. `execute` 保存 case 中的 requested command；首个可执行项由宿主解析后以绝对路径、宿主平台写入 adapter invocation。所有参数继续使用 `shell=False` 的数组调用，不重新拼接为 shell 字符串；解析或启动失败命中 `HC-EXECUTABLE-RESOLUTION`。Playwright/Godot 工具版本探针使用独立的 180 秒有界冷物化预算；超时命中 `HC-ADAPTER-TOOL-PROBE`，不得冒充正式 case 失败。Windows 候选工作树使用短临时根和仅作用于当前 Git 命令的 `core.longpaths=true`；执行产生长路径或未跟踪依赖后仍必须移除工作树及其 Git 注册。清理失败不得覆盖原始执行失败；只有在没有更早失败时才以 `HC-EXECUTION-WORKTREE-CLEANUP` 成为主结果。
2. Bootstrap 在 `.vibe-control/.gitattributes` 写入并绑定 `evidence/** -text -filter -working-tree-encoding`。执行前和验证时核对该文件受 Git 跟踪且有效；提交后逐项比较工作副本 SHA-256 与 `HEAD` Git blob，失败命中 `HC-EVIDENCE-GIT-BYTE-POLICY`。
3. case `lifecycle` 缺省为 `CANDIDATE_EXECUTION`；`BOOTSTRAP_DIAGNOSTIC` 只用于接入检查，不能满足规则/能力覆盖，也不能进入 task required cases。违反时命中 `HC-CASE-LIFECYCLE-SCOPE`。
4. `automation --action commit` 接受可选单行 `--message`；缺省为 `chore(governance): record <taskId> milestone`。空标题、换行或控制字符被拒绝；commit hook 失败时保留工作文件、撤销本次 staging，并返回 hook stdout/stderr。
5. Dashboard 只调用与 `validate` 共用的无副作用 projection。顶层状态使用 derived phase/health/claim，declared state 单独展示；自动 checkpoint 只有在其全部 required cases 都具备合格、候选绑定的 PASS evidence 且满足 counters/artifacts 预期时才显示 PASS。
6. `upgrade --plan [--spec]` 只读绑定旧/新 package、runtime、matrix、治理锁、case catalog、Git HEAD、确认记录和失效集合。`upgrade --apply <plan-hash> --spec` 先在 staging 中完整验证，将旧 runtime 与全部 task 后对象归档并生成逐文件 manifest，再原子替换；失败恢复旧控制面。旧 evidence/review/decision/handoff 只作历史诊断，新状态回到 `DRAFT / BLOCKED / DIAGNOSTIC`。

## 验收检查点

1. Windows 上锁定 `pnpm` 可解析为真实 `.cmd` 并执行；不存在的命令稳定阻断，shell 注入文本不能改变参数边界；含长受管路径的候选可从短工作树物化，执行生成 `node_modules` 后可完整清理，且清理异常不会遮蔽原 case 异常。
2. 在根级 `* text=auto eol=lf` 下，CRLF/二进制 evidence 的工作副本、Git blob 与 fresh clone 哈希相同；删除或漂移嵌套 attributes 后 fail-closed。
3. bootstrap-only case 不能锁入任务；porcelain 首行路径不丢失；默认/显式提交标题可用，hook 拒绝不留下控制器 staging。
4. 一项多 case checkpoint 只有部分 PASS 时 Dashboard 显示 `PENDING/BLOCKED`；declared `CLEAR` 与 validate `FAILED` 冲突时展示 derived `FAILED`；生成前后 state/evidence 字节不变。
5. upgrade 能检测计划漂移、脏工作树和错误哈希，中途失败可恢复，旧 PASS 不继承；MarkLuck 只重跑本地 Web journeys 与 V2S fail-closed case，并在外部证据或人工复核点停止。

## 证明上限

MarkLuck 已观察到的 Chromium `28/28`、Vitest `856`、TypeScript、ESLint、Stylelint、Prettier 与生产构建通过，只证明其原覆盖范围内未发现产品回归。它们不能把失效的控制面证据重新包装为正式 PASS；反过来，控制面失败也不能被叙述成产品功能失败。

本文件与用户批准的《vibe-control 0.3.7 Windows 执行、证据闭包与 Dashboard 修复》计划共同构成本任务需求事实源。
