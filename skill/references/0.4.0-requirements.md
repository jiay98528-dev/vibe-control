# vibe-control 0.4.0 可观察自动协作需求

本文件是 0.4.0 的版本需求事实源。它不得替代 [KEY_OBJECTIVES.md](../KEY_OBJECTIVES.md)，也不得把开发包自测外推为正式封印。

## 目标与姿态

- 核心 Schema 升级到 `4.0`，版本保持 `0.4.0 DEVELOPMENT_DIAGNOSTIC`。
- `formalClaimsAllowed=false`，开发包最高声明 `DEVELOPMENT_CHECKED`。
- 不创建 release/audit tag，不修改既有项目或治理包。
- 保留确定性最低证据核心；把阶段顺序、审计频次、风险到审核形式的映射和一般加固项改为项目派生建议。

## 必须实现

1. `bootstrap / adopt / start / resume` 在任何项目写入或提问前先初始化本机进度账本和离线仪表台。
2. 新项目与 3.2 升级项目默认使用 `AUTO_LOCAL_TO_REVIEW / MILESTONE_COMMITS / NONE`；默认权限不包含 push、merge、rebase、remote、PR、tag、release、不可逆操作或人工批准。
3. 协调后端按 `TEAM → SUBAGENT → SERIAL` 解析。宿主要求创建持久 Team 前显式授权时才询问；否则直接使用。Skill 不设置子智能体数量上限。
4. Coordinator、Implementer、Executor、Auditor 和 Owner 分工明确。实现者只运行与改动直接相关的快速开发检查；冻结候选后的完整 case 和独立审核由不同上下文负责。
5. Task 锁定候选绑定的里程碑、四域计分项、项目派生验证策略、guard policy 和报告策略。冻结后改变这些输入会失效下游对象。
6. 每个执行、门禁和审计报告最后附加零背景、无控制面术语的普通话说明，解释功能、已做事项、可用性、缺口、用户后果、能否继续和能否发行。
7. 普通节点只更新账本和仪表台，不打断自动推进。真正停止时显示两个具体行动候选和一个开放输入；宿主有结构化提问工具时必须调用。
8. 仪表台展示功能、健壮性与安全、审计、流程规范四个可复算比率和固定权重综合准备度，同时明确它不是剩余工时预测，也不具备证据或批准效力。

## 硬边界与软流程

`ACTION_GUARD`、`CLAIM_GUARD`、`HUMAN_DECISION`、`ENVIRONMENT_BLOCKED` 与 `ADVISORY` 必须分离：

- 权限扩大、路径越界、不可逆操作、R3 和远端冲突是动作停止边界。
- 候选/哈希/引用/证据漂移、零执行、skip、计数不守恒和 case 缺口只阻止声明；若修复仍在原合同内，自动流程可以继续。
- 主观质量、产品方向、范围和授权交还 Owner。
- 普通流程建议、风格意见和超出当前目标的探索只进入后续建议。

固定阶段、固定审计卡点或固定风险模板不得代替任务的 `verificationStrategy`。Auditor 完成锁定检查点后必须停止；除非命中当前目标、最低证据核心或权限边界，不得扩大威胁模型。

## 验证边界

- 证明仪表台可以在无 Git、无控制面、执行中、失败和候选待复核状态初始化、更新、重建和手动清除。
- 证明 revision 冲突不会丢失跨会话记录，Dashboard 生成不修改项目、state 或 evidence。
- 证明四域比率、综合准备度和普通话说明可复核，未知项不会制造高分。
- 证明 Team、需授权 Team、SubAgent 与 Serial 路径都保持单写控制面和角色声明真实。
- 证明实现任务包不携带完整审计答案，Executor/Auditor 使用冻结候选和锁定预期。
- 证明普通建议不阻断、最低核心仍 fail-closed、重复失败无代码变化时停止为 `PAUSED_NO_PROGRESS`。
- 复跑继承回归并让 package validator 继续保持 `BLOCKED / DIAGNOSTIC`。
