## 已确认有效但不得外推的能力

- Skill/runtime manifest 与受管文件的字节数、SHA-256 校验。
- 候选后产品、case catalog 和 transcript 漂移失效。
- 脏工作树阻断。
- skip、零执行、计数守恒等原 11 项 fixture 覆盖到的行为。

这些能力不能证明 Schema 被执行、逐 case 真实观察、跨对象身份闭包、审核独立、人工批准或 R2/R3 放行。

## 根因模式

1. **规范—执行漂移**：把文档中的 MUST 当成运行时已经实现。
2. **对象局部有效**：只验证单文件或局部字段，没有验证跨对象身份、时序和上限。
3. **自报等同观察**：把 evidence 中的声明字段当成外部执行事实。
4. **状态聚合过浅**：用“现有检查全绿”直接生成资格，遗漏 health 和阶段前置。
5. **正向夹具偏差**：测试主要证明已写代码能工作，没有主动攻击公开承诺。
6. **接口语义混写**：Skill 的模型路由、CLI 命令和用户可依赖协议没有区分。
7. **自审闭环**：实现者设计自己的测试集合，再用该集合证明完整性。

## 发行语义纠偏（后续设计输入）

后续复核发现，首个 RC 的修复把“高阶段必须有候选绑定的独立审核与人工决定”过度收紧成“所有 R2/R3 都必须使用 Ed25519，并且所有正式资格都必须有 release receipt”。这混淆了三件不同的事：Skill 自身的本地安装/版本 tag、项目的私有运行，以及项目面向外部的正式发行。密码学并不能自动证明审核者真实独立，也不应成为个人本地开发的密钥管理负担。

纠偏后的闭包是：

- 项目 bootstrap 前由用户明确选择 `LOCAL_EXPERIMENT | PRIVATE_OPERATION | EXTERNAL_RELEASE`，不得由模板默认或代理推断；
- R2 与私有 R3 仍要求候选绑定、独立 actor/session、原始审核 transcript、无开放 P0/P1 和 owner 决定，但记录不强制签名，真实性保留为人工边界；
- 仅 `EXTERNAL_RELEASE + risk=R3 + maxClaimLevel=RELEASE_READY` 使用 executor/auditor/release-auditor/owner 的 Ed25519 公钥与 receipt 闭包；私钥永不进入 Skill、runtime 或项目受管目录；
- `LOCAL_EXPERIMENT`、`PRIVATE_OPERATION` 分别硬封顶 `VERIFIED`、`ACCEPTED`，外部发行任务才可能达到 `RELEASE_READY`；
- 此纠偏不删除历史审计事实，而是把 F-EXT-002 的真正闭合条件限定为“不可伪造高阶段前置闭包”，不再把密码学本身当作 R2 的产品质量 oracle。

对应回归必须同时证明：未选择发行意图时 bootstrap 失败；本地实验不能 accept/release；私有 R3 在无密钥时仍可经独立审核与 owner 决定到 `ACCEPTED`；外部 R3 正式发行缺任一角色公钥、签名或 receipt 时 fail-closed。

## 0.2.1：Windows 受管决定路径身份

正式 `v0.2.0` 的新鲜黑盒补充审计报告 SHA-256 为 `6d823a677fc3e24fb25ba2d12d936965ecdb696f8981548f52755bc304736321`。报告建立 P1 `VC-V020-BB-001`：在 `PRIVATE_OPERATION` 合法链中，若调用者先把决定作为已跟踪的 `.vibe-control/decisions/d.json` 提交，而对象 `decisionId` 为 `D`，`accept` 返回 PASS 并推进到 `ACCEPTED`，但提交后 `validate` 命中 `HC-DECISION-TRACKED` 与 `HC-STATE-DERIVED-MISMATCH`，正式资格回落为 `DIAGNOSTIC`。

主线程复核确认根因不是审核缺失，而是 Windows 大小写不敏感文件系统与 Git 精确路径身份的交界：`accept` 以规范名 `D.json` 原子替换同一文件，目录项大小写随之改变，Git 索引仍跟踪 `d.json`。因此，机器状态已经推进，但重新派生时无法确认决定文件受跟踪。修复规则是：当输入决定与规范输出在文件系统上是同一文件时，保留调用者已有路径拼写并原位原子写入；不得为了规范化文件名破坏 Git 索引身份。回归必须从受管目录内的非规范大小写输入出发，依次提交决定、执行 `accept`、提交控制面并重新 `validate`，最终达到真实 `ACCEPTED`，且不得出现上述两个检查 ID。该反例关闭前不得以常见的目录外决定输入 happy path 外推 Windows 正式路径。

同轮主线程补查建立 P1 `VC-V020-DEP-001`：运行环境缺少 `jsonschema` 或 `cryptography` 时，第三方模块在 CLI 错误边界建立前导入，用户得到 Python traceback 而非稳定 `DEPENDENCY_BLOCKED` envelope。锁文件版本篡改测试不能证明缺包路径。修复要求入口 shim 仅用标准库先解析 dependency lock、核对 Python 与全部精确包版本，再导入控制器；预检失败或第三方 import 失败都必须 exit 2、`formal.eligible=false`、无 traceback。确定性回归使用隔离的 `python -S` 到达真实缺包入口。

`v0.2.1` 首轮最终候选黑盒审计又建立 P2 `VC-V021-BB-001`：`lock-task --contract` 收到项目外绝对路径时虽然 fail-closed、无 traceback，却因 `Path.relative_to` 的裸 `ValueError` 只返回 `CLI-INTERNAL-ERROR`，无法区分越界输入与控制器内部故障。修复要求所有进入内容引用的路径先执行项目边界、`..`、符号链接、存在性和 Git tracked 检查，越界稳定命中 `HC-PATH-SAFETY`；通用内部错误不得成为已知坏输入的正式接口。

R2/R3 缺口复审建立 P1 `VC-V021-BB-002`：bootstrap 从正在执行的源码 runtime 目录做无过滤 `copytree`，会把 package/runtime manifest 明确排除的 `__pycache__/*.pyc` 一并复制进项目；项目提交这些缓存后，重新执行或 clone 可改变 pyc，导致工作树与大量绑定无关地漂移，合法高阶段路径无法稳定复现。主线程在普通 `setup_project` 中独立观察到 2 个 cache 目录和 7 个 pyc。修复要求入口在导入 runtime 前设置 `sys.dont_write_bytecode`，bootstrap/migrate 只复制 runtime manifest 明确登记的文件，且回归必须证明项目固定 runtime 不含 cache、pyc 也不受 Git 跟踪。

外部 R3 正向复审建立 P1 `VC-V021-BB-003`：保证矩阵允许 required case 分别由 `runtime-observed` 或 `blackbox-observed` 证据覆盖，但运行时在 `EXTERNAL_RELEASE + R3 + RELEASE_READY` 路径把所有 case 强制为 `blackbox-observed`，使控制器从冻结候选亲自执行的 runtime case 永远不合格。根因是把“外部黑盒证据必须由 executor 签名”错误扩张成“外部发行的全部证据都必须是外部黑盒证据”。修复必须恢复混合可信证据边界：`execute` 产生的 runtime case 继续由候选 detached worktree 和逐 case provenance 保证；仅 blackbox case 要求 external attestation，并在外部 R3 时验证 executor 签名。review、owner decision、external release audit 与 receipt 的签名闭包保持不变。回归必须证明外部 R3 的控制器本地 runtime case 能推进到 `VERIFIED`，同时仍因缺审核而 fail-closed；另需由真实双 case 正向链证明 runtime 与签名 blackbox 可以共同达到 `RELEASE_READY`。
- 文档、Schema 或新增 happy-path fixture 不能单独解除限制；
- 修复必须按保证闭包逐项完成，不能用总测试数、提交速度或叙述性摘要替代。

## 0.2.2：最终候选审计未进入正式资格聚合

`v0.2.1` 复审建立 P1 `VC-V021-AUD-001`：static validator 只读取保证矩阵的实现状态、独立验证字段和 `formalClaimsAllowed`，manifest builder 随后信任该结果。审核者在两个独立临时 clone 中分别只改 runtime 和只改 test，重新生成 manifest 后仍得到 `FORMAL_GATE_READY`。这说明当时系统证明的是“矩阵说控制已实现”，不是“当前最终候选已经被独立审计”。

根因是把三个不同事实压进同一布尔值：内容完整、控制实现闭合、最终候选外审闭合。矩阵既描述义务又能授权正式姿态，package manifest 又把该自报传播给 runtime；候选 commit/tree、最终 package manifest 和审计报告从未进入资格聚合点。因此，任何审计后修改都不会自动失效。

0.2.2 的固定修复逻辑是：

- `package-manifest.json` 只登记内容，最高为 `AWAITING_EXTERNAL_VALIDATION`；static matrix validator 最高为 `CONTROL_IMPLEMENTATION_READY`，两者均固定 `formalClaimsAllowed=false`；
- 新增 `CTRL-CONFIRMED-011` 与独立 package release validator，固定比较 clean HEAD/tree、annotated release tag、annotated audit-report blob tag、package/runtime/matrix SHA-256、审核者 actor/session、PASS 结果、P0/P1 计数和完整控制 ID 集；
- `vibe-control-audit/v0.2.2` 指向机器可读审计报告 blob，`v0.2.2` 指向同一最终候选 commit 且其 tag message 为内容绑定收据；轻量 tag、缺失 tag、错误对象类型、报告替换、身份重合、非 PASS、开放 P0/P1、脏工作区或任一哈希漂移均 fail-closed；
- bootstrap 先验证安装 Skill 的实时 tag/object 闭包，再将规范化包级收据复制到项目治理目录并写入 governance lock。项目固定 runtime 重新核对收据与复制后的 package/runtime/matrix 哈希；
- 包级 tag 不使用私钥，不是授权、收费或公开分发机制，只声明本地内容绑定和误改检测，不能抵御拥有仓库写权限的恶意维护者；项目 `EXTERNAL_RELEASE` 的 Ed25519 链仍是另一套项目级边界；
- `.vibe-control/**` 作为 dogfood 记录受 Git 跟踪但从 Skill package manifest 排除，避免治理记录反向改变被审内容候选。

必须永久保留的最小回归包括：审计后提交 runtime 变化、审计后只提交 test 变化、缺/轻量/漂移 tag、三项内容哈希漂移、报告替换、审核身份重合、非 PASS、P0/P1 非零、脏工作区和无 Git 副本。测试只能在临时 Git 仓库创建真实 annotated tag；不得用环境变量或测试标志绕过生产 package gate。

## 0.3.3 检查点契约与审计漂移根因

后续真实项目审计暴露了新的流程根因：里程碑虽有目标、case 和最终 gate，却没有在任务开始前逐项锁定“什么外部结果算通过、哪些事实尚未证明、何时审核必须停止”。审核者在没有预期结果边界时，会把“多找问题”当作任务，逐轮扩大到 verifier 的 verifier、候选与验证器串通等被当前威胁模型排除的假设，并把真假问题的裁决成本转给产品负责人。

这不是单纯的 reviewer 提示词问题，而是规范—Schema 漂移：0.3.2 已要求关键目标、治理预算和停止条件，但 `task-contract`、evidence、review 与 owner decision 没有机器可消费的 checkpoint set、预期结果或停止闭包。文本规则无法阻止跨会话审核继续扩张。

同时固化两个 finding admission 反例：

- 项目级 `KEY_OBJECTIVES.md` 中存在、但当前 task 未引用的宽泛目标，曾可被 reviewer 用作 `CURRENT_GOAL_DEFECT` blocker。修复后该分类必须引用当前 task checkpoint，并证明 objective 属于该 task 与 checkpoint。
- finding 只声明影响 `RELEASE_READY` 时，旧阻断逻辑可能按“高等级问题”向下污染 `VERIFIED`。修复后 `affectedClaims[]` 必须形成向上闭包，运行时只阻断明确列出的当前 claim。

0.3.3 的控制逻辑为：定位中的 success signal/human gate 使用内容派生 ID；task 在实现前一次确认 checkpoint 摘要；case oracle 固定退出码、stdout/stderr 与 artifact 下限；checkpoint hash 传播到候选及全部下游对象；review 由控制器重算逐项 observed result；owner 逐项决定 HUMAN checkpoint；普通探索发现每候选最多三项，全部 required checkpoint 报告后审核停止。最低核心与 KF 安全越界仍可在未预设时阻断，但必须引用固定 core control 或锁定 failure mode，不能凭严重度扩张。

Schema 3.1→3.2 迁移采用两阶段内容绑定计划：旧控制面完整字节归档、逐文件 manifest、staging 完整验证和原子替换；旧 task/candidate/evidence/review/decision/receipt/handoff 全部失效并回到 `DRAFT / BLOCKED / DIAGNOSTIC`。迁移不自动决定 checkpoint 语义，也不把历史 PASS 重新包装为 3.2 资格。
